3DS Gallery – Cloudinary Migration Guide
=========================================

This guide explains how to migrate all existing pictures (previously stored as
local files on the web server) to Cloudinary, and how to update the database so
that the "path" column for each picture contains a valid Cloudinary public_id
instead of a legacy file-system path.

After completing this guide the application will work entirely through Cloudinary
and no legacy fallback code will be needed.


────────────────────────────────────────────────────────────────────────────────
OVERVIEW OF THE LEGACY STORAGE FORMAT
────────────────────────────────────────────────────────────────────────────────

Legacy pictures were saved with paths like:

  Picture\{id}.JPG          (2D picture, stored under the web root)
  Picture\{id}.MPO          (3D picture original)

A picture is identified as "legacy" in the old code by checking whether its
"path" column value has a file extension (e.g. ".JPG", ".MPO").

A picture is identified as "Cloudinary" when "path" has NO file extension – it
is a Cloudinary public_id of the form:  Picture/{id}

After migration every row should have a Cloudinary public_id in "path".


────────────────────────────────────────────────────────────────────────────────
PREREQUISITES
────────────────────────────────────────────────────────────────────────────────

1. A Cloudinary account with the following credentials available:
     - Cloud Name      (CloudinaryCloudName in Web.config)
     - API Key         (CloudinaryApiKey    in Web.config)
     - API Secret      (CloudinaryApiSecret in Web.config)

2. Access to the production SQL Server database.

3. Access to the web server's file system where the legacy Picture/ directory
   lives (or a full backup/copy of that directory).

4. The Cloudinary CLI tool OR a script using the Cloudinary REST API.
   The examples below use the official Cloudinary CLI (npm install -g cloudinary-cli)
   but the same operations can be done via the REST API or SDK.


────────────────────────────────────────────────────────────────────────────────
STEP 1 – IDENTIFY LEGACY PICTURES IN THE DATABASE
────────────────────────────────────────────────────────────────────────────────

Run this SQL query to find all pictures that still use legacy paths:

    SELECT id, path, type
    FROM   Picture
    WHERE  path LIKE '%.JPG'
       OR  path LIKE '%.MPO'
       OR  path LIKE '%.jpg'
       OR  path LIKE '%.mpo';

Take note of the results. You will need this list in Step 3.

If you want a complete export:

    SELECT id, path, type
    INTO   #LegacyPictures
    FROM   Picture
    WHERE  path LIKE '%.%';   -- any extension


────────────────────────────────────────────────────────────────────────────────
STEP 2 – UPLOAD LEGACY FILES TO CLOUDINARY
────────────────────────────────────────────────────────────────────────────────

For each legacy picture you must upload:

  a) 2D pictures (type = '2D')
     - Upload the .JPG file as an IMAGE resource with public_id = "Picture/{id}"

  b) 3D pictures (type = '3D')
     - Upload the left-eye .JPG as an IMAGE resource with public_id = "Picture/{id}"
     - Upload the right-eye image.
       The right-eye JPEG was extracted from the MPO at upload time and is NOT
       stored separately on disk. You must re-extract it from the .MPO file
       (see note below) and upload it with public_id = "Picture/{id}_r"
     - Upload the original .MPO file as a RAW resource with
       public_id = "Picture/{id}_mpo"  (no file extension in the public_id)

  NOTE on extracting eyes from an MPO file:
    An MPO file is two concatenated JPEGs.  Use the MpoParser class logic or
    any standard MPO splitting tool (e.g. ffmpeg, StereoPhoto Maker, or a
    custom script that splits on the JPEG SOI marker 0xFF 0xD8 after the first
    image) to obtain the two JPEG byte streams.

EXAMPLE UPLOAD COMMANDS (using curl / Cloudinary REST API)
----------------------------------------------------------

Replace <cloud_name>, <api_key>, <api_secret>, and <id> with real values.
TIMESTAMP = current Unix timestamp
SIGNATURE = SHA1( "overwrite=true&public_id=Picture/<id>&timestamp=<TIMESTAMP><api_secret>" )

2D JPEG upload:
    curl -X POST https://api.cloudinary.com/v1_1/<cloud_name>/image/upload \
         -F "file=@/path/to/Picture/<id>.JPG" \
         -F "public_id=Picture/<id>" \
         -F "api_key=<api_key>" \
         -F "timestamp=<TIMESTAMP>" \
         -F "signature=<SIGNATURE>" \
         -F "overwrite=true"

Left-eye JPEG (same command as 2D, just the left image byte stream):
    curl -X POST https://api.cloudinary.com/v1_1/<cloud_name>/image/upload \
         -F "file=@/path/to/left_<id>.jpg" \
         -F "public_id=Picture/<id>" \
         ...

Right-eye JPEG (public_id ends in _r):
    curl -X POST https://api.cloudinary.com/v1_1/<cloud_name>/image/upload \
         -F "file=@/path/to/right_<id>.jpg" \
         -F "public_id=Picture/<id>_r" \
         ...

Original MPO as RAW (public_id ends in _mpo, NO extension):
    SIGNATURE_RAW = SHA1( "overwrite=true&public_id=Picture/<id>_mpo&timestamp=<TIMESTAMP><api_secret>" )
    curl -X POST https://api.cloudinary.com/v1_1/<cloud_name>/raw/upload \
         -F "file=@/path/to/Picture/<id>.MPO" \
         -F "public_id=Picture/<id>_mpo" \
         -F "api_key=<api_key>" \
         -F "timestamp=<TIMESTAMP>" \
         -F "signature=<SIGNATURE_RAW>" \
         -F "overwrite=true"

AUTOMATION TIP:
  Write a small script (PowerShell, Python, or C#) that:
  1. Queries the database for all legacy rows (Step 1).
  2. Loops over each row, builds the correct public_id ("Picture/{id}").
  3. Uploads the file(s) using the Cloudinary SDK or the REST API above.
  4. Logs success / failure per picture id.


────────────────────────────────────────────────────────────────────────────────
STEP 3 – UPDATE THE DATABASE "path" COLUMN
────────────────────────────────────────────────────────────────────────────────

After every picture has been successfully uploaded to Cloudinary, update the
database so that the "path" column holds the Cloudinary public_id.

For every legacy picture the new public_id follows this pattern:

  Picture/{id}     (a forward-slash, never a backslash; no file extension)

Run this SQL to update all legacy rows at once:

    UPDATE Picture
    SET    path = CONCAT('Picture/', CAST(id AS VARCHAR(20)))
    WHERE  path LIKE '%.%';    -- rows that still have a file extension

VERIFICATION – after the update, no row should have an extension:

    SELECT COUNT(*)
    FROM   Picture
    WHERE  path LIKE '%.%';    -- should return 0

If it returns 0 you are done.

ROLLBACK PLAN:
  Before running the UPDATE, take a backup:

    SELECT id, path
    INTO   Picture_path_backup_YYYYMMDD
    FROM   Picture;

  To revert:

    UPDATE p
    SET    p.path = b.path
    FROM   Picture p
    JOIN   Picture_path_backup_YYYYMMDD b ON b.id = p.id;


────────────────────────────────────────────────────────────────────────────────
STEP 4 – VERIFY THE MIGRATION
────────────────────────────────────────────────────────────────────────────────

1. Browse the live site and spot-check several pictures (2D and 3D) to confirm
   they load from Cloudinary URLs (res.cloudinary.com/...).

2. Test a 3D picture download on a real Nintendo 3DS console to confirm the
   MPO file is served correctly from the OriginalMpo action.

3. Test the delete flow for at least one 2D and one 3D picture to confirm that
   the Cloudinary assets are removed.

4. Check the home page, gallery preview tiles, and user profile page to ensure
   thumbnails load correctly.


────────────────────────────────────────────────────────────────────────────────
STEP 5 – CLEAN UP OLD LOCAL FILES (OPTIONAL)
────────────────────────────────────────────────────────────────────────────────

Once you are satisfied that all pictures are loading from Cloudinary and the
database has been fully updated, you may remove the legacy Picture/ directory
from the web server to free up disk space.

  WARNING: Do NOT delete local files until you have confirmed that:
    a) Every picture row in the database has been updated (Step 3 verification).
    b) All Cloudinary uploads completed successfully (check your upload logs).
    c) The live site shows no broken images.

  Recommended: keep a compressed archive backup of the Picture/ directory for
  at least 30 days after the migration before permanently deleting it.
