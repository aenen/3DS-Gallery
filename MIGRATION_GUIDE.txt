3DS Gallery – Cloudinary Migration Guide
=========================================

This guide explains how to migrate all existing pictures (previously stored as
local files on the web server) to Cloudinary, and how to update the database so
that the "path" column for each picture contains a valid Cloudinary public_id
instead of a legacy file-system path.

After completing this guide the application will work entirely through Cloudinary
and no legacy fallback code will be needed.


────────────────────────────────────────────────────────────────────────────────
OVERVIEW OF THE LEGACY STORAGE FORMAT
────────────────────────────────────────────────────────────────────────────────

Legacy pictures were saved with paths like:

  Picture\{id}.JPG          (2D picture, stored under the web root)
  Picture\{id}.MPO          (3D picture original)

A picture is identified as "legacy" in the old code by checking whether its
"path" column value has a file extension (e.g. ".JPG", ".MPO").

A picture is identified as "Cloudinary" when "path" has NO file extension – it
is a Cloudinary public_id of the form:  Picture/{id}

After migration every row should have a Cloudinary public_id in "path".


────────────────────────────────────────────────────────────────────────────────
PREREQUISITES
────────────────────────────────────────────────────────────────────────────────

1. A Cloudinary account with the following credentials available:
     - Cloud Name      (CloudinaryCloudName in Web.config)
     - API Key         (CloudinaryApiKey    in Web.config)
     - API Secret      (CloudinaryApiSecret in Web.config)

2. Access to the production SQL Server database.

3. Access to the web server's file system where the legacy Picture/ directory
   lives (or a full backup/copy of that directory).

4. The Cloudinary CLI tool OR a script using the Cloudinary REST API.
   The examples below use the official Cloudinary CLI (npm install -g cloudinary-cli)
   but the same operations can be done via the REST API or SDK.


────────────────────────────────────────────────────────────────────────────────
STEP 1 – IDENTIFY LEGACY PICTURES IN THE DATABASE
────────────────────────────────────────────────────────────────────────────────

Run this SQL query to find all pictures that still use legacy paths:

    SELECT id, path, type
    FROM   Picture
    WHERE  path LIKE '%.JPG'
       OR  path LIKE '%.MPO'
       OR  path LIKE '%.jpg'
       OR  path LIKE '%.mpo';

Take note of the results. You will need this list in Step 3.

If you want a complete export:

    SELECT id, path, type
    INTO   #LegacyPictures
    FROM   Picture
    WHERE  path LIKE '%.%';   -- any extension


────────────────────────────────────────────────────────────────────────────────
STEP 2 – UPLOAD LEGACY FILES TO CLOUDINARY (BULK – ~4 000 PICTURES)
────────────────────────────────────────────────────────────────────────────────

Because there are thousands of files and the Cloudinary web interface does not
support raw MPO uploads, use the official Cloudinary CLI (cld) to perform a
bulk upload from the command line.

For each legacy picture you must upload:

  a) 2D pictures (type = '2D')
    - Upload the .JPG file as an IMAGE resource with public_id = "Picture/{id}"

  b) 3D pictures (type = '3D')
    - Upload the left-eye .JPG as an IMAGE resource with public_id = "Picture/{id}"
    - Upload the right-eye .JPG with public_id = "Picture/{id}_r"
      (The right-eye JPEG is NOT stored separately on disk.  It must be
      re-extracted from the .MPO file – see "MPO SPLITTING" below.)
    - Upload the original .MPO file as a RAW resource with
      public_id = "Picture/{id}_mpo"  (no file extension in the public_id)

  NOTE on extracting eyes from an MPO file:
    An MPO file is two concatenated JPEGs.  Split on the second JPEG SOI
    marker (0xFF 0xD8) using the Python script in sub-step 2b below, or any
    standard MPO splitting tool (e.g. StereoPhoto Maker, ffmpeg).


SUB-STEP 2a – INSTALL AND CONFIGURE THE CLOUDINARY CLI
-------------------------------------------------------

   # Requires Python 3.8+
   pip install cloudinary-cli

   # Set credentials once (stored in ~/.cloudinary)
   cld config --cloud_name <cloud_name> \
               --api_key    <api_key>    \
               --api_secret <api_secret>

   # Verify:
   cld whoami


SUB-STEP 2b – SPLIT MPO FILES INTO LEFT / RIGHT JPEGS
------------------------------------------------------

Run the following Python script from the directory that contains the Picture/
folder.  It reads every .MPO file, splits it into two JPEG files, and saves
them as:

   Picture/<id>_left.jpg
   Picture/<id>_right.jpg

   -----------------------------------------------------------------------
   # split_mpo.py
   import os, struct

   PICTURE_DIR = "Picture"
   SOI = b"\xff\xd8"

   for fname in os.listdir(PICTURE_DIR):
       if not fname.upper().endswith(".MPO"):
           continue
       fpath = os.path.join(PICTURE_DIR, fname)
       pic_id = os.path.splitext(fname)[0]          # e.g. "12345"
       with open(fpath, "rb") as f:
           data = f.read()

       # Find the second SOI marker (skip the first one at offset 0)
       second_soi = data.index(SOI, 2)

       left_bytes  = data[:second_soi]
       right_bytes = data[second_soi:]

       with open(os.path.join(PICTURE_DIR, f"{pic_id}_left.jpg"),  "wb") as f:
           f.write(left_bytes)
       with open(os.path.join(PICTURE_DIR, f"{pic_id}_right.jpg"), "wb") as f:
           f.write(right_bytes)

       print(f"Split {fname}: left={len(left_bytes)}B  right={len(right_bytes)}B")
   -----------------------------------------------------------------------

Run it:

   python split_mpo.py


SUB-STEP 2c – BULK UPLOAD 2D JPEGS
------------------------------------

Upload all .JPG files (2D pictures and left-eye 3D pictures) in one command.
The --public-id-prefix flag maps the local directory structure to the Cloudinary
folder, and --unique-filename false ensures the public_id matches the filename.

   cld uploader upload_dir Picture/ \
       --resource-type image         \
       --upload-preset ""            \
       --folder ""                   \
       --public-id-prefix Picture    \
       --unique-filename false       \
       --use-filename true           \
       --overwrite true              \
       --include-hidden false        \
       --exclude "*.MPO" --exclude "*.mpo" --exclude "*_right.jpg"

This uploads:
  - Picture/12345.JPG  → public_id = "Picture/12345"   (2D pictures)
  - Picture/12345_left.jpg → public_id = "Picture/12345_left"  (will be renamed in 2e)

NOTE: upload_dir is available in cloudinary-cli ≥ 3.0.
     Confirm with:  cld --version


SUB-STEP 2d – BULK UPLOAD RIGHT-EYE JPEGS WITH _r SUFFIX
----------------------------------------------------------

The right-eye files must be stored with the suffix _r (e.g. "Picture/12345_r").
Because the filenames end in _right, upload them separately with a rename step
using the Python script below, OR upload them via the SDK in sub-step 2f.

Quickest approach – use the Cloudinary CLI upload with a Python wrapper that
renames on the fly:

   -----------------------------------------------------------------------
   # upload_right_eyes.py
   import os, subprocess

   PICTURE_DIR = "Picture"

   for fname in os.listdir(PICTURE_DIR):
       if not fname.endswith("_right.jpg"):
           continue
       pic_id   = fname.replace("_right.jpg", "")   # e.g. "12345"
       public_id = f"Picture/{pic_id}_r"
       fpath     = os.path.join(PICTURE_DIR, fname)
       cmd = [
           "cld", "uploader", "upload", fpath,
           "--resource-type", "image",
           "--public-id",     public_id,
           "--overwrite",     "true",
       ]
       print(f"Uploading {fpath} → {public_id}")
       result = subprocess.run(cmd, capture_output=True, text=True)
       if result.returncode != 0:
           print(f"  ERROR: {result.stderr.strip()}")
       else:
           print(f"  OK")
   -----------------------------------------------------------------------

   python upload_right_eyes.py

If you have thousands of 3D pictures, add multiprocessing to parallelise:

   -----------------------------------------------------------------------
   # upload_right_eyes_parallel.py
   import os, subprocess
   from concurrent.futures import ThreadPoolExecutor, as_completed

   PICTURE_DIR  = "Picture"
   MAX_WORKERS  = 8          # adjust to taste; Cloudinary free tier allows ~10 req/s

   def upload(fname):
       pic_id    = fname.replace("_right.jpg", "")
       public_id = f"Picture/{pic_id}_r"
       fpath     = os.path.join(PICTURE_DIR, fname)
       result = subprocess.run(
           ["cld", "uploader", "upload", fpath,
            "--resource-type", "image",
            "--public-id",     public_id,
            "--overwrite",     "true"],
           capture_output=True, text=True
       )
       return fname, result.returncode, result.stderr.strip()

   files = [f for f in os.listdir(PICTURE_DIR) if f.endswith("_right.jpg")]
   print(f"Uploading {len(files)} right-eye images with {MAX_WORKERS} workers …")

   with ThreadPoolExecutor(max_workers=MAX_WORKERS) as pool:
       futures = {pool.submit(upload, f): f for f in files}
       for fut in as_completed(futures):
           fname, rc, err = fut.result()
           print(f"{'OK' if rc == 0 else 'ERR'} {fname}" + (f" – {err}" if err else ""))
   -----------------------------------------------------------------------

   python upload_right_eyes_parallel.py


SUB-STEP 2e – BULK UPLOAD ORIGINAL MPO FILES AS RAW RESOURCES
--------------------------------------------------------------

MPO files must be uploaded as resource_type=raw because the Cloudinary web
interface and image pipeline do not handle the MPO format.  The public_id must
NOT include a file extension.

   -----------------------------------------------------------------------
   # upload_mpo_raw.py
   import os, subprocess
   from concurrent.futures import ThreadPoolExecutor, as_completed

   PICTURE_DIR  = "Picture"
   MAX_WORKERS  = 8

   def upload_mpo(fname):
       pic_id    = os.path.splitext(fname)[0]        # strip .MPO
       public_id = f"Picture/{pic_id}_mpo"
       fpath     = os.path.join(PICTURE_DIR, fname)
       result = subprocess.run(
           ["cld", "uploader", "upload", fpath,
            "--resource-type", "raw",
            "--public-id",     public_id,
            "--overwrite",     "true"],
           capture_output=True, text=True
       )
       return fname, result.returncode, result.stderr.strip()

   files = [f for f in os.listdir(PICTURE_DIR) if f.upper().endswith(".MPO")]
   print(f"Uploading {len(files)} MPO files as raw with {MAX_WORKERS} workers …")

   with ThreadPoolExecutor(max_workers=MAX_WORKERS) as pool:
       futures = {pool.submit(upload_mpo, f): f for f in files}
       for fut in as_completed(futures):
           fname, rc, err = fut.result()
           print(f"{'OK' if rc == 0 else 'ERR'} {fname}" + (f" – {err}" if err else ""))
   -----------------------------------------------------------------------

   python upload_mpo_raw.py


SUB-STEP 2f – RENAME LEFT-EYE UPLOADS IN CLOUDINARY (3D pictures only)
------------------------------------------------------------------------

The bulk upload in 2c stored the left-eye images with public_ids like
"Picture/12345_left".  They need to be "Picture/12345" (same as the 2D path).
Use the Cloudinary CLI rename command:

   -----------------------------------------------------------------------
   # rename_left_eyes.py
   import os, subprocess
   from concurrent.futures import ThreadPoolExecutor, as_completed

   PICTURE_DIR  = "Picture"
   MAX_WORKERS  = 8

   def rename(fname):
       pic_id      = fname.replace("_left.jpg", "")
       old_public  = f"Picture/{pic_id}_left"
       new_public  = f"Picture/{pic_id}"
       result = subprocess.run(
           ["cld", "uploader", "rename", old_public, new_public,
            "--overwrite", "true"],
           capture_output=True, text=True
       )
       return fname, result.returncode, result.stderr.strip()

   files = [f for f in os.listdir(PICTURE_DIR) if f.endswith("_left.jpg")]
   print(f"Renaming {len(files)} left-eye assets …")

   with ThreadPoolExecutor(max_workers=MAX_WORKERS) as pool:
       futures = {pool.submit(rename, f): f for f in files}
       for fut in as_completed(futures):
           fname, rc, err = fut.result()
           print(f"{'OK' if rc == 0 else 'ERR'} {fname}" + (f" – {err}" if err else ""))
   -----------------------------------------------------------------------

   python rename_left_eyes.py

   ALTERNATIVE: If you prefer to skip the rename step, change split_mpo.py
   (sub-step 2b) to save the left-eye file as "{id}.jpg" (without the _left
   suffix) and adjust the upload_dir exclude pattern in 2c accordingly.


────────────────────────────────────────────────────────────────────────────────
STEP 3 – UPDATE THE DATABASE "path" COLUMN
────────────────────────────────────────────────────────────────────────────────

After every picture has been successfully uploaded to Cloudinary, update the
database so that the "path" column holds the Cloudinary public_id.

For every legacy picture the new public_id follows this pattern:

  Picture/{id}     (a forward-slash, never a backslash; no file extension)

Run this SQL to update all legacy rows at once:

    UPDATE Picture
    SET    path = CONCAT('Picture/', CAST(id AS VARCHAR(20)))
    WHERE  path LIKE '%.%';    -- rows that still have a file extension

VERIFICATION – after the update, no row should have an extension:

    SELECT COUNT(*)
    FROM   Picture
    WHERE  path LIKE '%.%';    -- should return 0

If it returns 0 you are done.

ROLLBACK PLAN:
  Before running the UPDATE, take a backup:

    SELECT id, path
    INTO   Picture_path_backup_YYYYMMDD
    FROM   Picture;

  To revert:

    UPDATE p
    SET    p.path = b.path
    FROM   Picture p
    JOIN   Picture_path_backup_YYYYMMDD b ON b.id = p.id;


────────────────────────────────────────────────────────────────────────────────
STEP 4 – VERIFY THE MIGRATION
────────────────────────────────────────────────────────────────────────────────

1. Browse the live site and spot-check several pictures (2D and 3D) to confirm
   they load from Cloudinary URLs (res.cloudinary.com/...).

2. Test a 3D picture download on a real Nintendo 3DS console to confirm the
   MPO file is served correctly from the OriginalMpo action.

3. Test the delete flow for at least one 2D and one 3D picture to confirm that
   the Cloudinary assets are removed.

4. Check the home page, gallery preview tiles, and user profile page to ensure
   thumbnails load correctly.


────────────────────────────────────────────────────────────────────────────────
STEP 5 – CLEAN UP OLD LOCAL FILES (OPTIONAL)
────────────────────────────────────────────────────────────────────────────────

Once you are satisfied that all pictures are loading from Cloudinary and the
database has been fully updated, you may remove the legacy Picture/ directory
from the web server to free up disk space.

  WARNING: Do NOT delete local files until you have confirmed that:
    a) Every picture row in the database has been updated (Step 3 verification).
    b) All Cloudinary uploads completed successfully (check your upload logs).
    c) The live site shows no broken images.

  Recommended: keep a compressed archive backup of the Picture/ directory for
  at least 30 days after the migration before permanently deleting it.
